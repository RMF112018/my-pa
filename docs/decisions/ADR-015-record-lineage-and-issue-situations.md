## Context

MY-PA holds native records that each own their own lifecycle: Situations, Projects, Meetings and immutable Meeting note versions, Tasks, Commitments, Constraints, Entities, Captures and Knowledge Assertions. Nothing answers *why* two of them are related, *which Issue* a record concerns, or *what exact source passage* a Commitment came from, and nothing lets a reader start from any one of them and recover the same scoped history. Free-form `object_refs` on a Situation, a shared Project, a shared Meeting Series, a shared date or a shared participant are not evidence of causation, and an LLM client that infers a link is not an authority for it.

The review package found that the predecessor design would have introduced a phantom-prone `linkable_record_refs` registry (AR-001), evidence that could be added to an earlier revision after the fact (AR-002), Capture roots presented as immutable versions (AR-003), a second Project-membership owner beside `project_situations` (AR-004, AR-019), cross-Issue traversal through a shared Meeting (AR-007), missing principal-composite foreign keys (AR-014) and a proposal row that was both mutable and append-only (AR-021). Every remote OAuth client authenticates as the operator Principal ([ADR-013](ADR-013-fixed-local-principal-and-operator-auth-grants.md)), so the Principal alone cannot tell the human operator from a model client.

## Decision

1. **A+C, not B.** An Issue is an existing `knowledge.situations` row (`sit_`) whose new, immutable `kind` column is `issue_workstream`; every other Situation is `kind = 'context'` and is not converted, re-typed or re-read. Issues gain a `version` with compare-and-swap and an immutable revision ledger. Associations between records are rows in a typed, Principal-partitioned association ledger (C). There is no `Issue` table, no `issue_` identifier kind, no Case family, no graph database, no queue and no service outside the modular monolith ([ADR-001](ADR-001-modular-monolith-two-processes.md)).
   - **B (a separate Case aggregate) is rejected** because it duplicates lifecycle, Project scope, Principal partition and migration identity for an object Situations already model, and two owners of "the thing this work is about" cannot both be canonical. B may be revisited only by a superseding ADR on evidence of one of: a tenancy or retention rule that an Issue must obey and a context Situation must not; a lifecycle that cannot be expressed as Situation states plus Issue revisions; or a legal-hold or disclosure boundary that differs between Issues and contexts. Convenience, naming or UI grouping are not grounds.
   - **C alone is rejected** because a link ledger with no closure container cannot carry an Issue's lifecycle, closure basis or Project scope.
   - Converting an existing context Situation into an Issue is **not** part of this decision; `kind` is fixed at insert. A future `issues.specialize` capability needs its own ADR amendment and evidence rules.

2. **Native owners stay native.** Project↔Situation membership is owned by the existing `knowledge.project_situations`; S1 makes the new `issues.project_links.add`/`end` capabilities its only live writer for Issues and records every change in an append-only `issue_project_membership_events` ledger. Task→Commitment follow-up, Meeting→Series, Meeting→note versions, Constraint `FOLLOW_UP_OF`, Entity `member_of`, Capture and Managed Document version chains and Knowledge Assertion evidence stay with their owners and are exposed to lineage reads as `native_virtual` edges; they are never copied into the association ledger. Record lifecycles never cascade: closing an Issue, Task, Commitment or Constraint changes no other record's state.

3. **Immutable root, revision, evidence, head.** One association is one immutable root row (`record_links`) carrying its kind, typed endpoints, relation type, membership role, Issue context and canonical semantic identity. Every change is a new immutable revision (`record_link_revisions`) with a sequential number, an action, a lifecycle state, a server-derived acceptance basis and authority, and a frozen evidence set. Evidence is attached **to the revision**, never to the root: a revision's evidence rows are written in the revision's transaction and the database refuses any later addition. The current state is a head projection (`record_link_heads`) that the database keeps equal to the latest revision and that can be rebuilt from roots and revisions alone; the head is not a fact. No generic registry of linkable records exists: each endpoint is validated against its native table under a row lock in the writing transaction (decision 9).

4. **Evidence-set digest and canonical serialization.** A revision stores `evidence_set_digest = sha256(b"lineage-evidence-set-v1\n" + canonical_json)` in lowercase hex. The canonical JSON is ADR-014 decision 6's encoding — NFC strings, `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)`, UTF-8, no floats, every fixed key present with explicit `null` — of `{"schema_version": 1, "anchors": [...]}`, where each anchor object carries exactly `source_family`, `source_root_id`, `source_version_kind`, `source_version_id`, `source_version_no`, `source_sha256`, `passage_start_cp`, `passage_end_cp`, `passage_sha256` and `role`, and the list is sorted by that tuple with `null` ordered before any value. Server-minted anchor identifiers are **excluded**, so the same evidence produces the same digest in any revision. The empty set is legal for revisions that need no evidence and has its own fixed digest. The same encoding with prefix `b"lineage-request-v1\n"` is the request digest (decision 11) and, without a hash, is the stored `normalized_identity` of a root (decision 6).

5. **Passage anchors are code-point slices of the stored body.** For a Meeting note version the source digest is the stored `content_sha256` (`sha256` of the exact stored Markdown, UTF-8). A passage is `[passage_start_cp, passage_end_cp)`, zero-based and end-exclusive, counted in Unicode code points of the **stored, unnormalized** string — not bytes, not grapheme clusters and not an NFC rendering — and `passage_sha256 = sha256(slice.encode("utf-8"))`. NFC applies to the canonical JSON strings of decision 4, never to the note body. A client that hashed a normalized or re-rendered body gets a mismatch, which is refused; the server never searches for, re-bases or retargets a passage, and never resolves "the latest note". `legacy_unversioned` names a reference to a Capture root (`cap_`) that pins no version; it is an explicitly limited claim that can never satisfy an exact-version requirement, and no Meeting note is ever copied into a synthetic Capture.

6. **Closed relation taxonomy and direction.** Relations are a closed, versioned matrix of `(from family, to family, relation type)` with a per-entry evidence rule; an unregistered combination is refused, and a new entry needs an ADR amendment, a migration widening the database CHECK and tests. The full vocabulary is `issue_member` (kind `issue_membership`, written only through `issues.memberships.*`), and the directed semantic types `originated_from`, `delegated_from`, `escalated_from`, `discusses`, `blocks`, `created_to_resolve` and `related_context` (kind `semantic`). Direction is stored as asserted: `originated_from` points from the derived work to its source, `discusses` from the Meeting or note to the subject. `related_context` is the one symmetric type and stores its endpoints in canonical order once. Membership, a shared Project, Series, time or participant is never causal evidence, discussion never proves origin, and there are no numeric confidence scores. Slice S1 admits `issue_member`, `originated_from` and `discusses`; the rest are specified now and admitted in S2. `normalized_identity` is the canonical JSON of schema version, kind, relation type, both endpoints with their selectors, membership role and Issue context; the database enforces at most one **active** head per identity.

7. **Actor and authority are derived, never supplied.** No request field carries a Principal, actor, acceptance basis, review decision, authority class or server timestamp; strict request models reject them. A lineage write reuses ADR-014's `derive_knowledge_review_authority` with the exact operator-review client allowlist and an **empty** Knowledge Manager allowlist, because a Knowledge Manager is a model client. A write that creates or changes accepted lineage — an association, an Issue membership, an Issue Project link — requires the derived class `local_operator` or `remote_operator_attested`, records it with its decision channel on the revision, and is stored with acceptance basis `user_confirmed`; any other caller is `denied`. An AI or ordinary client may only ever create a proposal, never an accepted link; the proposal and review capabilities (`records.associations.propose`/`review`, immutable proposal roots and decisions with a rebuildable head per AR-021) are specified for S3 and absent in S1. Issue metadata writes (`issues.create`, `issues.update`) record the derived class but are open to any admitted caller, since they assert nothing about other records. Closing or reopening an Issue (S2) requires operator attestation, a closure evidence set and the absence of unresolved mandatory members, and any exception is an operator decision, never risk acceptance by an agent (OD-03, OD-08).

8. **Time and availability are separate dimensions.** `recorded_at` (known time) is server-stamped on every immutable row. Business-effective time (`valid_from`/`valid_to`, `valid_at` queries) and `known_at` as-of selection are S3; until then every read is the current recorded state and says so, and a missing former native field value is reported as `partial_native_history`, never reconstructed. Source availability (`available`, `archived`, `restricted`, `redacted`, `unavailable`, `withdrawn`, `superseded`, `legacy_unversioned`) is reported independently of a link's lifecycle state (`active`, `ended`, `contested`) and of its acceptance basis; a source becoming unavailable later never rewrites an accepted revision.

9. **Endpoint validation and lock order.** There is no common endpoint lock helper in the repository, so this ADR defines one order: within one transaction a lineage writer first reserves its idempotency row, then locks the Issue Situation(s) it changes `FOR UPDATE` in identifier order, then locks every other native endpoint and evidence parent row `FOR SHARE` in `(family token, identifier)` order, then locks the association head `FOR UPDATE`. A `FOR SHARE` row lock is honoured by every native writer without code changes, because PostgreSQL makes any `UPDATE` or `DELETE` of the row wait for it; this is the "common lock" CR-002 requires. Each endpoint is checked for strict `IdKind`, Principal ownership, the correct native parent (a note version's Meeting) and its family's linkability rule. A reference to a missing record and a reference to another Principal's record are answered identically with `not_found`, before any row is written.

10. **Append-only database enforcement.** Roots, revisions, evidence anchors, revision evidence, Issue revisions and Issue Project membership events carry a `BEFORE UPDATE OR DELETE` refusal trigger raising `restrict_violation` (precedent `7d9a450dfd07`) and a `BEFORE TRUNCATE` statement refusal (precedent `c8e4a1b70d35`). The head projection admits exactly one transition per revision and nothing else. The idempotency row admits one `reserved → completed` transition in its own transaction and can never be committed reserved (precedent `6734f039f7a6`). Every foreign key between lineage rows and onto native rows is principal-composite and `ON DELETE RESTRICT`. Least-privilege role separation (precedent `record_event_roles.py`, today Record Event only) is **not** extended in S1; the triggers bind every non-superuser role including the owner, and runtime-role provisioning for lineage relations is an operator-gated follow-up with CR-014.

11. **Idempotency and compare-and-swap.** Every lineage write carries an `idempotency_key` of 1 to 128 characters, scoped like `meeting_write_requests` to `(principal_id, capability, idempotency_key)`. A replay with the same request digest returns the recorded outcome with `replayed: true` and writes nothing; the same key with a different digest is `conflict`. Revision and Issue writes carry `expected_revision`/`expected_version`; a stale value is `conflict`. Asserting an association whose identity already has an active head is a no-op that returns the existing association with `created: false` and never changes or upgrades its authority; adding evidence to it is an explicit `records.associations.correct` revision.

12. **Disclosure.** All reads are Principal-scoped. Lineage and Issue reads return metadata, identifiers, digests and offsets, never source bodies. A historical note body is revealed only by `meetings.notes.read_version`, a separate capability under its own purpose. A cross-Principal or absent identifier is `not_found`, including the Issue context of a lineage read; responses carry no hidden-node counts.

13. **Naming, compatibility and recovery.**
   - Capability families: `issues.*` for Issue lifecycle, `issues.memberships.*` for Issue scope over non-Project records, `issues.project_links.*` for the native Project link, `records.associations.*` for semantic assertions, `records.lineage` for the bounded read, `meetings.notes.versions`/`read_version` for immutable note lookup, and later `programs.*`. Not `continuity.issues.*`. Each new capability is classified `CHATLLM_OPERATOR_DECISION_REQUIRED` until the operator decides its exposure; no grant is issued by any change under this ADR.
   - Compatibility: S1 adds new capabilities only and changes no existing request or response. `continuity.situations`, `meetings.read` and the Work plane keep their exact v1 shapes (an Issue is listed by `continuity.situations` as the Situation it is, with no new field), the strict web client keeps every existing `gateway.json` entry and decoder byte-for-byte (S1 adds only the two entries its related-Issue display calls, `records.lineage` and `meetings.notes.read_version`), and the existing Work `origin_evidence_ref` parser (`cap_` root or accepted `asrt_` capture assertion) is unchanged. A change to an existing contract (CR-010's Commitment Project fields, CR-006's `association_intents`) must be an explicit negotiated version, never a silent extra field.
   - Recovery: disabling the capabilities stops new lineage while leaving native records untouched. Heads are rebuilt from revisions. The schema revision's downgrade refuses while any lineage, Issue revision or membership event row exists, and no downgrade, cleanup or test deletes recorded facts.

14. **Repository-truth resolutions of the package.** Recorded so no implementer re-derives them:
   - `ires` collides with `IdKind.IDENTITY_RESOLUTION`; the S2 responsibility/handoff event uses `ihnd` instead. S1 prefixes are fixed in the contract.
   - `knowledge.situations` gains `UNIQUE (situation_id, principal_id)` and `UNIQUE (situation_id, principal_id, kind)` before any composite foreign key names it; Issue-only references bind the second, so the database proves an Issue is an Issue.
   - `project_situations` gains `UNIQUE (principal_id, project_id, situation_id)` and principal-composite foreign keys to `projects` and `situations`. Its existing rows are validated by the migration and never repaired, re-dated or given evidence: a Principal mismatch makes the upgrade refuse. Every existing row names a context Situation (Issues do not exist before S1, and `kind` is fixed at insert), so those rows keep their legacy meaning and S1 neither reads nor rewrites them; a new row naming an Issue must be accompanied by a membership event in the same transaction, which the database checks. The legacy `link_situation`/`close_situation` repository paths, unreachable from any capability, refuse Issue-kind Situations.
   - S1 admits **no** Record Event family. Adding `situation`/`record_link` families widens `record_family`, routing, provenance and the changefeed contract for no S1 acceptance test; the immutable Issue, link and membership revisions are themselves the transaction receipts, and the package's `link_mutation_event_receipts` table and Record Event emission are deferred to S3 behind their own admission.
   - `capture_versions` has no composite version target, is partitioned by `owner_principal_id` and cascades from `captures`. S1 admits only Meeting note version evidence; S2 adds `UNIQUE (version_id, capture_id, owner_principal_id)` and a `capture_version` anchor binding with `RESTRICT`, under which an attempted hard delete of an evidenced Capture fails rather than cascades.
   - The Knowledge Assertion family token `knowledge_assertion` means ADR-014's `kasr_`. Today's accepted Work evidence `asrt_` is an ADR-006 capture assertion; it is not a lineage family and is not admitted as lineage evidence.
   - `meetings.read` omits `content_sha256` and stays that way; `meetings.notes.versions` exposes it.
   - Public error codes are the repository's (`invalid_request`, `not_found`, `denied`, `conflict`, `unavailable`, `unsupported`); the package's `source_unavailable` maps to `unavailable` and `limit_exceeded` to `invalid_request` naming the bound.
   - Identifiers must be `IdKind` prefixes of at most 72 characters, not the package's looser `^[a-z]+_` pattern.

## Out of scope

- Any production use: live migration, backfill, grants, client profile changes, deployment and activation, each a separate operator gate (OD-07).
- Financial and Primavera P6 source models, imports and Program panels (CR-011, CR-012): fixtures and interface specifications only until OD-06 is decided.
- Automatic historical backfill or promotion of `object_refs`, shared Projects, Series, names or dates into accepted links (OD-05): only deterministic native virtual edges or independently source-backed assertions, by a separately authorized run.
- Program analytics and report manifests (CR-009, CR-010, CR-013), handled by their own work packages under this ADR's vocabulary.

## Consequences

- Each fact keeps one owner: native records their lifecycles, `project_situations` the Project scope of a Situation, the association ledger accepted semantic links, and Meeting note versions the source text.
- Lineage authority is bound to a human-operator surface or an explicitly allowlisted operator-review client; model clients can read and, from S3, propose.
- Exact source anchoring makes an origin claim survive later note edits, at the cost that a client must quote the exact stored version and offsets.
- Widening the taxonomy or an evidence family is deliberately expensive: an ADR amendment, a migration and tests.

## Supersession

This ADR supersedes nothing. ADR-003, ADR-006, ADR-007, ADR-010, ADR-013 and ADR-014 are unchanged; ADR-014's canonical encoding and authority derivation are reused, not amended. A change to the digests, the identity encoding, the taxonomy, the authority rule or the native-owner rule needs an amendment to this ADR.
