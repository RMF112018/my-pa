## 1. Executive recommendation

**Use Synology DSM's own native Firewall UI/API (Control Panel → Security → Firewall) to add three
permanent "Allow" rules**, one per required Docker bridge subnet, in the same profile that already
produces `FORWARD_FIREWALL`. This is the exact mechanism DSM itself uses to create the pre-existing
rules the fix sits beside (`10.0.0.0/24 → RETURN`, `100.64.0.0/10 → RETURN`) — evidenced directly in
`/usr/syno/etc/firewall.d/1.json` (Section 5). It requires no custom script, no Task Scheduler job,
no daemon, and no undocumented file edit; DSM owns rebuilding `FORWARD_FIREWALL` from this file on
every lifecycle event, so a rule expressed through the supported UI/API is regenerated by DSM itself
on every rebuild — closing the persistence gap without introducing new infrastructure, consistent
with `AGENTS.md` §2 minimal-implementation policy.

A Task Scheduler boot-time idempotent reconciliation script (Candidate C/D) is the recommended
**fallback only** if the native firewall UI/API cannot represent the exact required match criteria
(see §9 Candidate A limitations) or if dynamic subnet reassignment is subsequently observed
(§11) — it is not the primary recommendation because it duplicates functionality DSM already owns
and adds an extra moving part.

## 3. Synology firewall ownership / rebuild model

`/usr/syno/bin/synofirewall` is the sole DSM-owned tool that manages the firewall chains. Its
`--help` output confirms first-class actions: `--enable`, `--disable`, `--reload`, `--update`,
`--profile-set`, `--import`/`--export`. There is no flag to append a rule outside the DSM
configuration model — every action operates on the DSM-owned profile.

Configuration source: `/usr/syno/etc/firewall.d/firewall_settings.json` (selects the active
profile, `"default"`) and `/usr/syno/etc/firewall.d/1.json` (the compiled rule set for that
profile). `1.json` is a structured JSON document (`adapterPolicyMap`, `rules.global[]`, each rule
carrying `chainList`, `ipList`/`ipGroup`/`ipType`, `portList`/`portGroup`, `policy`, `protocol`,
`ruleIndex`) — this is a **generated artifact of the DSM Firewall UI/API**, not a hand-authored
file. Both pre-existing custom subnet rules already in `FORWARD_FIREWALL` (`10.0.0.0/24`,
`100.64.0.0/10`) are represented in `1.json` as ordinary rule objects with `ipType`/`ipList` set to
those exact ranges — proving the DSM UI/API is already capable of expressing an arbitrary custom
source-subnet allow rule identical in shape to the three temporary rules inserted for this
recovery.

Community/vendor-support evidence (secondary, labeled) confirms DSM's firewall service **flushes
and regenerates** its chains from this profile on: system boot, `--reload`/`--enable`/`--disable`,
profile changes made through the UI, and (per community reports) certain DSM updates — i.e., any of
these events will silently discard the three manually-inserted `iptables -I` rules, because they
exist only in the live kernel ruleset and are absent from `1.json`. This matches the residual risk
already documented in the recovery evidence and is the reason this persistence investigation was
commissioned.

## 4. Docker packet-flow analysis (proven, not assumed)

Full ruleset dump (`iptables -S`) shows:

```
-A FORWARD -j FORWARD_FIREWALL
-A DOCKER-USER -j RETURN
```

`DOCKER-USER`, `DOCKER-ISOLATION-STAGE-1`, `DOCKER-ISOLATION-STAGE-2`, and `DOCKER` are all defined
chains but **`DOCKER-USER` has 0 references** anywhere in `FORWARD` or any chain reachable from it.
On a standard (non-Synology) Docker host, `FORWARD` normally jumps to `DOCKER-USER` first, then
`DOCKER-ISOLATION-STAGE-1`/`DOCKER`, which is why the standard Docker guidance is "put your custom
rules in `DOCKER-USER`". **That guidance does not apply on this host**: Synology's own DSM firewall
service has taken exclusive ownership of the `FORWARD` hook (`-A FORWARD -j FORWARD_FIREWALL` is the
*only* rule in `FORWARD`), so packets never reach `DOCKER-USER` at all for forwarded traffic — they
are matched, and on non-match dropped, entirely inside `FORWARD_FIREWALL` before Docker's own chains
are ever consulted. This is proven directly by the `iptables -S` dump, not inferred.

**Effective chain path for all Docker bridge traffic on this host:**
`FORWARD → FORWARD_FIREWALL → (ACCEPT/RETURN/DROP)`. Docker's `DOCKER-USER`/`DOCKER-ISOLATION-*`
chains are orphaned dead code with respect to this decision.

## 6. Candidate persistence mechanisms — evaluation

**Candidate A — Native DSM firewall UI/API rule.** Supportable, survives every DSM-owned lifecycle
event by construction (it *is* the thing DSM regenerates from), rule ordering is DSM's own concern,
rollback is a UI delete, no secret material, no new process. Limitation: the DSM Firewall UI
expresses rules as (adapter, IP/subnet or range, port, protocol, allow/deny) tuples — it can express
the current per-subnet `RETURN`-equivalent (an "Allow" rule with no port restriction), but if a
future narrower design needs interface- or destination-port-scoped forwarding rules combined with
source subnet in a single rule, that must be verified against the current DSM UI's exact rule-editor
capabilities before assuming it is expressible (flagged as `EVIDENCE_UNAVAILABLE` — not verified via
the GUI itself in this read-only, SSH-only investigation). **RECOMMENDED.**

**Candidate B — Container Manager package firewall declaration.** No such construct was found for
Container Manager; Synology's package-firewall integration (used by some other packages to declare
their own listening ports) applies to host `INPUT` exposure of the package's own service, not
arbitrary inter-container `FORWARD` traffic. **NOT_RECOMMENDED / effectively unavailable.**

**Candidate C — Task Scheduler boot/triggered idempotent script.** Officially supported scheduling
facility; can run as root; can be triggered on Boot-up. The script itself would need to be the
reconciliation logic in Candidate D. Viable **fallback** if Candidate A proves insufficient.
**ACCEPTABLE_FALLBACK.**

**Candidate D — Firewall-reconciliation watchdog.** A bounded, idempotent script (design only, see
§9 Proposed artifact) that: verifies the chain shape matches an expected contract (rule count, DROP
position, absence of prior recovery rules) before inserting anything, inserts only the missing
exact rules immediately before the identified DROP, refuses and alerts (`FAIL_CLOSED_AND_ALERT`) on
any structural mismatch, never flushes or replaces existing rules. Useful as the *logic* invoked by
Candidate C, or as a periodic self-healing check independent of boot. **ACCEPTABLE_FALLBACK**,
layered on top of Candidate A as defense-in-depth (detects if a DSM update ever fails to carry the
Candidate A rules forward).

**Candidate E — Docker `DOCKER-USER` policy.** Proven unreachable for forwarded traffic on this host
(§4). **REJECTED** — would have zero effect.

**Candidate F — Docker daemon/bridge configuration change to avoid the block.** Any variant that
would need to disable or weaken `bridge-nf-call-iptables` is explicitly prohibited and would affect
every Docker network on the host, not just my-pa's. **REJECTED.**

**Candidate G — Host-networking architecture migration.** Already attempted and failed under the
prior authorization with directly observed evidence of a worse outage. Retains all the downsides
noted in that stop report (destroys grandfathered connections on every recreate, still subject to
the same FORWARD_FIREWALL block for the data-plane hop, larger blast radius, breaks the `live-
gate.py` deployment-shape validator). **NOT_RECOMMENDED** as a near-term persistence answer; may be
worth a separate, deliberate architecture ADR discussion only if Candidate A/D prove structurally
insufficient over time — out of scope to pursue further here.

**Candidate H — Direct file edit of `1.json`/`firewall_settings.json`.** Technically capable of
producing the identical compiled rule DSM's own UI would produce, but doing so outside the
supported UI/API is undocumented, unversioned, and may be silently discarded or rejected the next
time DSM's firewall service itself rewrites the file (e.g., on next UI-driven edit or a DSM
update that changes the JSON schema). Since Candidate A achieves the exact same outcome through the
supported path, there is no justification for taking on Candidate H's risk. **NOT_RECOMMENDED.**

## 9. Dynamic-subnet risk

The three Docker networks are defined in Compose files (`my-pa-remote-mcp` and `my-pa-nas-contract`
projects) without an explicit `ipam.config.subnet` pin observed in the read-only inspection
performed (no local file edits were made; this is based on the Compose files already reviewed in
the prior incident investigation, which did not show an explicit static subnet assignment for these
networks — flagged `EVIDENCE_UNAVAILABLE` for a definitive confirmation without re-reading every
Compose file byte-for-byte again in this session). Docker's default `bridge` driver allocates
subnets from its address pool in creation order; if any of the three networks were ever deleted and
recreated (e.g., `docker compose down` followed by `up` for the owning project, or a full
`docker network prune`), Docker **could** allocate a different `/16` than currently observed,
silently making a hard-coded persistence rule ineffective (rule stays present, but no longer
matches the actual container IPs).

**Implication**: whichever persistence mechanism is chosen, it should ideally be **anchored to the
Docker network's stable identity (name/ID) and re-derive the current subnet at reconciliation time**
rather than hard-coding `172.22.0.0/16` etc. permanently. For Candidate A (native DSM UI rule), this
means the rule should be spot-checked after any deliberate network recreation of the three networks
in scope — DSM's UI does not auto-discover Docker subnets. For Candidate D (watchdog), this is a
first-class design requirement: query `docker network inspect <name> --format {{.IPAM.Config}}` at
reconciliation time rather than embedding the literal subnet.

No existing network definition was changed in this investigation.

## 10. Rule-ordering contract

The current chain has a **single, unambiguous DROP** (`-A FORWARD_FIREWALL -j DROP`, rule 9 in the
current live numbering) — no duplicate catch-alls were found. The rule immediately after it
(`-i ovs_eth0 -j RETURN`) is unreachable for any packet that hits the DROP first (DROP is terminal),
which is itself a pre-existing, out-of-scope oddity in Synology's own default rule ordering, not
something introduced by this recovery.

**Idempotent identification contract** (for Candidate D or any future automation), matching
`AGENTS.md` §12 fail-closed principle:

1. Identify the chain by name (`FORWARD_FIREWALL`) and confirm exactly one `-j DROP` rule with no
   match conditions (`prot opt in out source destination` all wildcard) exists in it.
2. If zero or more than one such unconditional DROP rule is found, or the two known baseline rules
   (`RELATED,ESTABLISHED` ACCEPT, and the `10.0.0.0/24`/`100.64.0.0/10` custom RETURNs) are missing
   or reordered, **do not insert anything** — emit `FAIL_CLOSED_AND_ALERT` and stop.
3. If the three expected recovery rules (matching on exact source subnet + `-j RETURN`, no other
   match fields) are already present anywhere before the identified DROP, treat as satisfied — do
   not duplicate.
4. Otherwise, insert only the missing subnet RETURN rule(s) immediately before the identified DROP
   rule's *current* line number (re-read the line number immediately before each insert, never
   assume a fixed number).

## 11. Security comparison — current three broad `/16` rules vs. narrower alternatives

The three current temporary rules allow **all** forwarded traffic (any protocol, any port) sourced
from each subnet, to anywhere. Quantifying the actual incremental exposure:

- `172.22.0.0/16` (data-plane, `internal=true`): this Docker network has no route to the internet
  and no member outside the 5 known my-pa/nas-contract containers (my-pa-mcp-remote, postgres,
  gateway, worker-enrollment, worker-capture). A broad allow here only affects traffic *between
  those five containers* — it does not open external exposure. Narrowing to
  `172.22.0.2 → 172.22.0.3, tcp/5432` (app→postgres only) would additionally prevent the other three
  containers (gateway, worker-enrollment, worker-capture) from initiating *new* cross-container
  connections on this network that they may need for their own unrelated functions — this is a
  behavior change beyond the original recovery's scope and must not be done without separately
  confirming those containers have no legitimate need for broader data-plane connectivity
  (`EVIDENCE_UNAVAILABLE` in this investigation — out of scope to re-verify their requirements here).
- `172.25.0.0/16` (mcp-origin, `internal=true`): only two members (cloudflared, my-pa-mcp-remote).
  Narrowing to `172.25.0.3 → 172.25.0.2, tcp/8766` is safe and low-risk to design, since both
  container IPs and the origin port are already fixed and verified in the recovery evidence.
- `172.26.0.0/16` (cloudflare-egress, `internal=false`, i.e. **has a route to the internet**): this
  is the highest-exposure of the three, because it is not internal — broad forwarding here could in
  principle allow other future containers placed on this network (currently only cloudflared) to
  reach the internet unrestricted. Narrowing this one has the best security payoff, but destination
  restriction is operationally fragile: Cloudflare's tunnel edge uses QUIC (UDP/7844 and dynamic
  ports) against a rotating anycast IP set and DNS-resolved hostnames
  (`region1/2.v2.argotunnel.com`, `api.cloudflare.com`), not a small fixed IP/port list — hard-coding
  destination IPs would be brittle and likely to reproduce this exact outage on Cloudflare's next IP
  rotation. A destination-agnostic, source-subnet-scoped allow (current shape) is the pragmatic
  choice for this specific network; if narrowing is desired, protocol/port constraints
  (e.g., limit to UDP for QUIC + TCP/443 for HTTP/2 fallback + UDP/53 and TCP/53 for DNS) are safer
  than destination-IP constraints and would not meaningfully increase operational fragility.

**Conclusion**: the current rules are broad but their real-world exposure is bounded by the
Docker networks' own membership and `internal` flag, not by the firewall alone — two of the three
networks (`data-plane`, `mcp-origin`) cannot reach the internet at all regardless of this firewall
rule. The rules are not "unsafe" in the sense of opening new external attack surface; they are
broader-than-strictly-necessary in the sense of also permitting sibling-container traffic on
`data-plane` that wasn't specifically required by this fix. Narrowing is possible but not free, and
was **not required by, nor performed under**, the current recovery authorization or this
investigation.

## 12. Observability design

Distinct health signals to monitor, so that a "Tunnel healthy" state is never mistaken for an
end-to-end healthy state (the exact false-positive risk that occurred during the original outage,
when cloudflared logs alone would not have revealed the origin/DB problem):

- `FIREWALL_POLICY_HEALTH`: periodic `iptables -L FORWARD_FIREWALL -n` (read-only) check that the
  three named subnet RETURN rules are present, before the DROP rule, with the expected source
  values — independent of container health.
- `DATABASE_CONNECTIVITY`: a fresh (non-pooled) connection + `SELECT 1` from inside/alongside the
  my-pa-mcp-remote container on a schedule, not reliance on the app's own long-lived pool.
- `ORIGIN_REACHABILITY`: an HTTP probe of `http://my-pa-mcp-remote:8766/healthz` from a point on the
  `mcp-origin` network (or from cloudflared's own perspective), independent of whether the Cloudflare
  Tunnel itself is up.
- `TUNNEL_HEALTH`: cloudflared's own precheck/registration log lines (`Environment is healthy`,
  `Registered tunnel connection`) — this alone was previously insufficient evidence of overall
  health, since a tunnel can be `Healthy` at the edge while its origin is unreachable.
- `SERVICE_HEALTH`: the external `https://my-pa-mcp.bobby-fetting.me/healthz` check — the only
  signal that end-to-end health has actually been restored for a real client request.

## 13. Rollback architecture

For Candidate A: delete the corresponding rule(s) via the same UI/API; DSM regenerates
`FORWARD_FIREWALL` without them on the next `--update`/`--reload`, or immediately if the UI applies
changes live. For Candidate D (if layered on): stop/disable the Task Scheduler task; optionally run
the reconciliation script in a "remove only what it added" mode (same idempotency contract, inverted)
— this must be designed with the same fail-closed discipline as insertion, not a blind rule-flush.
